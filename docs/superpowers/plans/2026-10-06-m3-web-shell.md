# M3 Web Shell Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The web app drives a `@cpt/core` session: a pilot picks an aircraft and a procedure, operates every control on a panel built from generic GA widgets or aircraft artwork, works the checklist in Guided, Practice or Free explore, sees the outside view of the current phase, reads the deviation summary, and switches language and theme. Device screens sit in the panel. Errors, missing images and a missing `localStorage` never break the app. Released as v0.4.0.

**Architecture:** `apps/web` is the composition root. `apps/web/src/trainer/` owns the one session per chosen aircraft and the app-level state (aircraft, procedure, mode); every feature reads it through hooks bound with `useSyncExternalStore`. Each feature lives in its own directory under `apps/web/src/` and brings its own `messages.ts`. `@cpt/panel-kit` holds language-neutral React widgets (controls, indicators, the artwork layer renderer) and the resolver that turns a declared `Appearance` into a widget; it receives resolved strings and positions as props and calls back on input. Core is unchanged except for one validator rule (Task 4).

**Tech Stack:** as M2, plus `jsdom`, `@testing-library/react` and `@testing-library/user-event` (dev, root) for component tests. No other new dependency without a recorded decision.

**Spec:** `docs/superpowers/specs/2026-10-05-cockpit-procedure-trainer-design.md`, sections 3, 4.1–4.3, 4.6, 4.8, 4.9, 5 (Modes, Screen, Persistence), 6, 7, 8 and 11 (M3 Web shell). Design: `docs/design/BRAND.md`, `docs/design/brief.md` (screen ids S1–S11), `docs/design/handoff/`.

**Issues:** #19 app shell, #20 panel renderer, #21 panel-kit controls, #22 panel-kit indicators, #23 artwork layer renderer, #24 gallery, #25 checklist pane and summary, #26 modes, #27 outside-view strip, #28 translations, #29 error handling and notice, #45 device screens, #95 type and spacing lint, #77 remaining Claude Design screens, #94 brand-bundle check, and the M2 follow-ups #101 and #110 (core, already in progress). #118 is the validator rule for continuous-lever action targets (Task 4).

**(d) Did the owner answer the M2 open questions on release PR #114?** No. The PR has no comments and no reviews. Question 4 (lever completion) is settled by this plan (Decision 9); questions 1–3 are unchanged and carried (see Open questions).

**(e) Does open question 4 touch the spec's decisions table?** No. The table (§2) has no row on lever travel, action targets or completion; §4.1 ("continuous 0–1 or named notches") and §4.7 ("the position to reach") are body text and stay true under Decision 9. The plan decides it.

## Vocabulary

- **trainer store** (#19): the app-level store in `apps/web/src/trainer/` holding aircraft, session, procedure and mode.
- **messages file**: a feature's `messages.ts`, built with `defineMessages` (#28).
- **widget**: a panel-kit React component for one control or indicator kind; **resolver**: the panel-kit function that picks the widget for an `Appearance` (#20).
- **mount stub**: a null-returning component created by an earlier task at the place a later task renders.

## Review Focus

1. **A stub that does not match its later owner's needs.** If #19's mount stubs or panel-kit types lack a prop a later task needs, that task would edit a closed issue's file in a busy wave. Reviewers of Tasks 5 and 14 check every interface listed under Interfaces exists with the stated signature.
2. **Language leaking into panel-kit.** A widget that imports a dictionary or hard-codes `ON`/`OFF` breaks the language switch on the panel. Reviewers grep `packages/panel-kit/src` for German or English UI words outside tests and the gallery fixtures.
3. **Brand on the panel.** A status ink or brand neutral inside a widget or the panel area breaks §6.2. Reviewers grep panel-kit and `apps/web/src/panel` for `--color-success`, `--color-warning`, `--color-danger`, and accent use outside the highlight and selection outline; `ui-verifier` checks it visually.
4. **Input blocked by the checklist.** Spec §5: input is never blocked. In Guided and Practice every control operates; only Free explore (operate toggle off) shows details instead. Pinned in Task 16.
5. **Exact lever targets.** A lever that cannot land exactly on 0 or 1 makes a Decision 9 action item uncompletable. Pinned in Task 8 by a drag-past-the-stop test.
6. **`localStorage` assumed.** Any unguarded access breaks private-mode tablets. Pinned in Task 11 by a whole-app render with a throwing `localStorage`.

## Decisions

1. **#19 is the scaffold owner.** It adds every dependency of the milestone, panel-kit's React dependency, the panel-kit barrel with stub sub-directories, the widget-props types and the mount stubs, so `pnpm-lock.yaml`, the package manifests and the barrel each have one owner. Same pattern as #11 in M2.
2. **Component tests opt into jsdom per file** with a `// @vitest-environment jsdom` docblock; `vitest.config.ts` stays unchanged and core tests stay in the node environment.
3. **Translations: per-feature messages files, no shared dictionary.** Each feature directory owns a `messages.ts` built with `defineMessages`, whose type makes a key missing in either language a compile error; a glob test over `**/messages.ts` checks every file at run time (same keys, no empty strings). Reason: parallel PRs in a wave never share a dictionary file, and removing a feature removes its strings. #19 writes its strings bilingually in `shell/messages.ts` as a plain object and renders English; #28 types that file and wires the switch in wave 2, when no other task touches `apps/web`.
4. **#28 runs before every other UI task in `apps/web`** (wave 2), so later tasks write translated text from their first commit.
5. **Panel-kit is language-neutral.** Widgets receive `label` and `positionLabels` as resolved strings; the panel renderer localizes aircraft `Text`.
6. **Panel hardware colours are tokens.** Realistic widgets need hardware colours (bezel, knob, legend, needle, lamp and arc colours) that are not brand colours. They are a theme-independent `--panel-*` group in `tokens.css`, recorded in a "Panel hardware" table in `BRAND.md` (kept equal by `tokens.test.ts`), added once by #19. Panel-kit and device screens reference them with `var()`; #95 extends the literal lint to `packages/panel-kit/src` and `packages/device-*/src/screen`. Reason: CLAUDE.md and spec §6.3 allow colours only in `tokens.css`, and §6.2 keeps the brand off the panel; a separate group satisfies both.
7. **The artwork renderer takes its fallback as a prop.** #23 does not import #21 or #22, so the three run in parallel; the resolver (#20) passes the generic widget as `fallback`.
8. **The gallery is a second Vite HTML entry served by `vite dev` only,** so it never ships in a production or UAT build and needs no router.
9. **M2 open question 4: an action item on a continuous lever may target only `0` or `1`.** The lever widget clamps to its travel, so a drag past either stop lands exactly on it and the engine's exact-equality rule is well defined. A setting in between ("throttle 1000 RPM") is a check item with a condition on the state, or the lever declares named notches. A new validator finding (Task 4) rejects other targets. Reason: no contract field, so nothing waits for #101's edit of `contract/types.ts`; the checklist engine is unchanged; it matches GA checklists, where intermediate power settings are read on a gauge. It changes no row of the spec's decisions table (pre-flight check e).
10. **A phase jump during a procedure asks for confirmation.** M2's `jumpToPhase` abandons the active procedure (M2 open question 3, unanswered); the confirmation makes that visible instead of silent. Switching to Free explore during a procedure ends it too (`setMode('explore')`, PR #127) and asks the same way.
11. **Device screens are registered next to devices, not inside them.** `device-registry.ts` gains `deviceScreens` keyed by device id; `deviceRegistry` and `createSession`'s `devices` option stay as they are, since core's `Device` type cannot hold a React component.
12. **#20 pre-creates the extension points of #26 and #45** (`PanelOverlay`, `usePanelInput`, `DeviceLayer`), so wave 5 never edits `apps/web/src/panel/`.
13. **The trainer store drives time** with an interval of core's exported step constant while the trainer is mounted; core keeps owning no timers.
14. **The aircraft and procedure picker (S5) is part of #19,** since it is the shell's start screen and the place of the start-up notice; #29 owns the notice component and #26 the mode behaviour.
15. **Wave 0 core work stays where it is:** no M3 task edits `packages/core/src/contract/` or `session/`, so #101 and #110 cannot collide with UI work.
