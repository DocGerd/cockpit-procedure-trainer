# M6 CTSL Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The club's Flight Design CT Supralight as the second registered aircraft: a representative analog panel in three views, a systems model built from core's blocks, the handbook's normal and emergency procedures in our own words, self-drawn gauge and control artwork, and the three avionics units of the analog variant as device packages. Released as v0.7.0.

**Architecture:** One new aircraft package, `packages/aircraft-ctsl`, split into one module per concern so the six aircraft issues own disjoint files. Task 1 creates every module and fixes the interfaces between them (control ids and positions, indicator ids, the systems state shape, failure ids, phase ids, device slots, the procedure record type); later tasks fill their own module and never edit `src/index.ts`. Three new device packages, `packages/device-sl40`, `packages/device-gtx327` and `packages/device-gpsmap496`, each installed and registered in its own PR. `apps/web` changes only in its two registries and `package.json`.

**Tech Stack:** as M4. No new dependency.

**Source of facts:** `docs/aircraft/ctsl-intake.md` (the intake record). Implementers have **no access** to the flight manual or to anything under `reference/`; the intake record is the source for every value, step and label. A fact it does not carry is a question for the orchestrator, not a guess.

**Spec:** `docs/superpowers/specs/2026-10-05-cockpit-procedure-trainer-design.md`, sections 4 (all), 7, 8, 9 and 11 (M6 CTSL). Content policy: `docs/content-policy.md`. Authoring guides: `docs/adding-an-aircraft.md`, `docs/adding-a-device.md`. Reference package: `packages/aircraft-demo`.

**Issues:** #37 intake (closed by the PR that adds this plan), #38 views and placements, #39 systems model, #40 normal procedures, #41 emergency procedures and failures, #42 artwork, #47 avionics (tracking), split into #210 SL40 COM radio, #211 GTX 327 transponder, #212 GPSMAP 496.

## Pre-flight checks

**(a) What exists?** `packages/aircraft-demo` is the reference aircraft: controls, indicators, systems, phases and procedures in `src/`, devices installed as `radio` and `xpdr`, stand-in devices in `src/test-devices.ts`. `apps/web/src/aircraft-registry.ts` lists the demo only; `apps/web/src/device-registry.ts` lists `com` and `transponder`. The registry tests (`aircraft-validation.test.ts`, `aircraft-widgets.test.ts`, `procedure-walkthrough.test.ts`) pick up every registered aircraft and device with no edit. `pnpm-workspace.yaml` covers `packages/*`. ESLint already has blocks for `packages/aircraft-*`, `packages/device-*` and `packages/device-*/src/logic/`, so no package kind is new and `tools/boundary.test.ts` needs no extension.

**(b) Who owns the lockfile?** CI runs `pnpm install --frozen-lockfile`, so every new workspace package and every new `apps/web` dependency changes `pnpm-lock.yaml`. Only one task per wave may own it: Task 1 (the aircraft package and its registration), then one device per wave. This is why the devices are spread over waves 2 to 4.

**(c) Can procedures live outside `index.ts`?** Yes. `defineAircraft` checks the assembled object against `ProcedureDefinition<S, CT, I, F, P>` from `@cpt/core`. Task 1 exports a `CtslProcedures` type from `src/types.ts`; each procedure module declares its record `as const satisfies CtslProcedures`, so a wrong control id or position fails to type-check in the module itself.

**(d) Lever rule (M3 Decision 9, #118).** An action item on a continuous lever targets only `0` or `1`. The CTSL checklists set the throttle to 4000 rpm, to idle, to about 10 % and to full, and the trim to neutral. Decision 3 makes throttle, trim, choke, brake and carb heat levers with named notches, so every checklist setting is an exact action target and the walk-through can perform it.

**(e) Guard state is not in `TrainerState`.** `TrainerState` exposes `controls`, `systems` and `devices`; guard positions live in the control store only. A check item cannot see whether the rescue-system safety pin (the guard) is out. Decision 4 keeps the handle `guarded`, as the spec's own example, and makes "armed" and "secured" confirm items. Exposing guard state to conditions is a core change outside M6 (open question 2).

**(f) Walk-through bound.** `walkProcedure` advances at most `MAX_STEPS` (2000) times `STEP_MS` (50 ms), 100 s of simulated time, while it waits for a check or a `holdUntil`. Every time-driven value a procedure waits for (oil pressure after start, flap travel, starter cranking) must settle well inside that, so the systems model uses compressed time constants where the real figure is longer (warm-up is minutes; the `holding` snapshot is already warm instead).

**(g) Zero procedures in wave 1.** Task 1 registers an aircraft whose procedure modules are empty until wave 3. The validator and walk-through accept that; Task 1's `ui-verifier` pass confirms the app shows the aircraft without procedures. If it does not, Task 1 stops and reports; it does not patch `apps/web`.

**(h) An action already satisfied completes on its own.** The checklist engine completes the current action item as soon as the control already sits at the target position (`settle` in `packages/core/src/checklist/checklist.ts`), and the walk-through treats an unchanged control as performed. So "parking brake set" at `holding`, where the snapshot already has it set, is a valid action item, but it proves nothing; Review Focus 4 applies to such items as it does to checks.

## Review Focus

1. **Facts not from the intake.** Every number, step and order in a procedure or the systems model traces to an intake section. A reviewer greps the constants and items against intake §4, §6, §7 and §8 and flags any value the intake does not hold, any non-conservative choice, and any reordering.
2. **Handbook wording.** No sentence reads like a translation of the handbook; labels are short; placards on the drawn panel are our own text. No manufacturer marks in SVGs or device screens.
3. **The lever rule.** No action item on a continuous lever with a target other than 0 or 1; #118's registry test runs.
4. **Walk-throughs that pass by accident.** A check whose condition is already true in the start snapshot proves nothing; reviewers of Tasks 5 and 6 ask, for each check, which earlier action makes it true, and mutate one action to confirm the check then fails.
5. **Wrong-operation scenarios.** Task 2's tests fail when the rule they name is removed (mutation per scenario).
6. **Representative-panel wording** stays in `name`, `handbookRevision` and the README.

### Task 2: CTSL systems model and scenario tests (Closes #39) — wave 2

**Files:** `packages/aircraft-ctsl/src/systems.ts`, `packages/aircraft-ctsl/src/systems.test.ts`, `changelog.d/39.added.md`

**Dependencies:** Task 1.

**Goal:** `step` drives every state field of Task 1 from the controls, the environment and the active failures, following intake §3.6 and §4, with every failure of `src/failures.ts` modelled.

**Behaviour (source: intake §3.6, §4.2, §4.4, §4.5):**

- Electrical: core's `electricalBus` for battery and generator (`battery` in = master on, `generator` in = generator on). Avionics bus = main bus and `avionicsMaster` on. Charge lamp state: main bus powered and not charging. Consumers follow their rocker and breaker.
- Ignition and engine: core's `pistonEngineStart`. `ignition` positions map to its magnetos; `start` engages the starter, which needs the main bus. The ignition does not need the bus: with BAT and GEN pulled a running engine keeps running. With `fuelValve` closed the key has no effect (the valve covers the slot) and a running engine stops after a short run-on. Cold start (oil below the warm threshold) needs `choke` on and `throttle` idle; choke on with the throttle open does not start. Starter cranking longer than 10 s stops cranking until it has cooled 2 min.
- Rpm per throttle notch from intake §4.2 (idle 1400; `low` about 2000–2500; `runup` 4000 on the ground; full about 5000 static, never above 5500 in level flight); one ignition circuit drops rpm within the intake's limits (pick a drop per side under 300 and a difference under 120, both named constants). Windmill relight per intake §4.2.
- Temperatures and pressure: oil pressure rises within 10 s of start into 2–5 bar; oil and CHT warm with power. Use compressed time constants so the values a procedure waits for settle inside the walk-through bound (pre-flight check f).
- Flaps: need the main bus and `flapBreaker` in. The selector preselects; flaps travel at a fixed rate (`flaps.moving` while travelling); extension stops (and `moving` stays true) when the airspeed exceeds the max flap speed of the next setting (intake §4.1). Override positions drive past the end detents while held there and stop at the end switch. `flapControlFailure`: detent positions have no effect; the override still works.
- Parking brake: closing `parkingBrakeValve` with `brake` on sets it; it holds until the valve opens.
- ELT: `eltTransmitting` when `elt` is `on`. Rescue system: `rescueDeployed` once `rescueHandle` is `pulled`.
- Failures: `generatorFailure` (no charging, charge lamp lit); `engineStoppage` (engine stops and will not restart while active); `engineFire` (`fire` true while fuel reaches the engine; out once the valve is closed and the engine has stopped, faster with the throttle full); `coolantLoss` (CHT climbs with power, holds below the red line at `low` power); `oilLoss` (oil pressure falls to zero, oil temperature rises, the engine stops later); `flapControlFailure` as above.
- `runningFrom(controls, environment)` returns a warm, settled state for the entry snapshots (oil at least 51 °C).

- [ ] **Step 1: Failing tests** (`systems.test.ts`, on a session from `createSession` with `{ devices: testDevices }`): starter with BAT pulled does not crank; start with the fuel valve closed fails; cold start without choke fails, with choke and throttle open fails, with choke and idle succeeds; starter held past 10 s stops cranking and works again after cooling; engine keeps running with BAT and GEN pulled; charge lamp lit with the engine stopped and BAT in, out once running with GEN in; avionics bus off with the Avionics Master off; flaps do not move without bus or breaker; flaps reach the selected setting and `moving` clears; flaps do not extend past the max flap speed; override drives beyond −12° and 35°; parking brake sets only in the right order; each failure produces the reaction above; ignition left and right drops are within limits at `runup`; every entry snapshot is warm where intake §5 says so.
- [ ] **Step 2: Implement** until green. Named constants for every value; no comments repeating figures.
- [ ] **Step 3: Fragment:** `The CT Supralight's electrical system, engine, fuel valve, flaps, brakes and failures behave as its handbook describes.`

## Decisions

1. **#37 is closed by this plan and the intake record, without photos.** Owner decisions 1 and 2 (2026-10-06) replace its bullets: the panel is self-drawn from the handbook's description and called representative; the installed avionics are the analog variant's units from the handbook; the handbook revision is recorded (intake §1). The ask for club material moves to intake §9. Likewise #38's "every control from the photos" and #42's "look like the real panel" read against intake §3.
2. **The CTSL package is split into one module per concern, and Task 1 creates all of them.** Reason: every issue would otherwise edit `src/index.ts`; with fixed interfaces, waves 2 and 3 run three agents each without a shared file.
3. **Throttle, trim, choke, brake and carb heat are levers with named notches.** Reason: M3 Decision 9 allows only 0 and 1 as action targets on continuous levers, and the checklists set the throttle to run-up, start and cruise settings and the trim to neutral. The notches are the checklist settings, so Guided can highlight them and the walk-through can perform them.
4. **The rescue handle is `guarded` with the safety pin as its guard; "armed" and "secured" are confirm items.** Reason: guard state is not visible to conditions (pre-flight check e); a separate pin toggle would invent hardware. Deployment is an action on the handle.
5. **The starter is the ignition key's spring-back `start` detent,** not a momentary button, as on the aircraft.
6. **The fuel valve is a two-position toggle and the key interlock is behavioural:** with the valve closed the key has no effect. Reason: the store never blocks input (spec decision "Step order").
7. **BAT and GEN are `breaker` controls** (push-pull switch-breakers), initial `pulled`.
8. **Carb heat is a provisional console control.** Reason: seven checklists and the take-off placard name it; without a control Guided has no target. Flagged in intake §9.
9. **The intercom and the ELT remote are aircraft controls, not device packages, and the altitude encoder is an input.** Reason: with no audio (spec §4.9) the intercom has nothing to model beyond its switch and breaker; the ELT remote is a switch and a lamp; the encoder has no controls. #47's units are the SL40, the GTX 327 and the GPSMAP 496.
10. **Each device is a new package per unit,** not an extension of `device-com` or `device-transponder`. Reason: spec §4.9 asks for the specific unit's logic and manual revision; a device may not import another device.
11. **The device issues were opened by the planner** (#210, #211, #212, under #47), so the plan cites real numbers, as M4 did with #123.
12. **Devices run one per wave.** Reason: each new package changes the lockfile, which only one task per wave may own.
13. **#39 owns every failure's behaviour; #41 owns the emergency procedures and their tests.** Reason: both issues claim "the model reacts"; one owner of `systems.ts` per wave.
14. **The rescue deployment is trained as an engine failure with no landable field,** injecting `engineStoppage`. Reason: the handbook's only route to it besides a failed spin recovery is the emergency landing's first step; no flight-dynamics failure exists to inject.
15. **Spin, stall, rollover and EMS failure are not trained.** Reason: no flight-dynamics model, and no EMS in the analog variant.
16. **The generator failure procedure is club-authored** and marked so; the handbook has none.
17. **Radio and transponder steps in Task 5's checklists are confirm items,** and the device-operating checklist is Task 7's own module. Reason: Task 7 installs the transponder in the same wave.
18. **Altitudes are above the field and the trainer models no real aerodrome.**
19. **Product names and model numbers are allowed as plain text for a real aircraft and its real units** (Flight Design, CT Supralight, Rotax 912, Garmin SL40, GTX 327, GPSMAP 496); marks, logos, artwork and manual text are not. Reason: M4's Review Focus 5 banned names because the demo is fictional; spec §4.9 asks each device to name the specific unit and its manual revision. `docs/content-policy.md` already bans only artwork, logos and copied content.
